Issue #0036 — LLM JD 抽取器（required_skills + evidence） — 2026-07-30

Design Decisions

Decision required_skills / responsibilities 必填，仅 seniority 带默认

Ambiguity: Pydantic 惯例是全字段给默认值，但默认 extra="ignore" 下，空 JSON {} 或键名走样（{"skills": ...}）会静默校验通过，返回空抽取结果。

Choice: required_skills / responsibilities 无默认值（键缺失 → ValidationError → 走重试→JDExtractionError 链路）；seniority 保留 "mid" 默认与 prompt「default to mid when unclear」一致。

Rationale: review 第 1 轮 finding：spec 要求「不返回半成品」，静默空结果比显式失败更难排查（#037 会拿空技能 JD 污染匹配）。

Decision 专用异常 JDExtractionError（llm_extractor 用的是 ValueError）

Ambiguity: issue 明确要求抛 JDExtractionError，但「与 llm_extractor.py 风格一致」的既有实现抛 ValueError。

Choice: 定义在 jd_extractor.py 内的专用异常类，其余重试/截断/自我修正逻辑与 llm_extractor 完全同构。

Rationale: #037 的 API 层需要精确 catch 抽取失败映射 502，ValueError 太宽会误捕其他错误；验收条件优先于模式一致性。

Decision critical 内联在技能项上，critical_skills 作派生属性

Ambiguity: issue 说输出结构含 required_skills / critical_skills 两个列表；spec 的 JSON 示例则是技能项内联 critical 布尔。

Choice: 按 spec JSON 建模（ExtractedSkill.critical + evidence），JDExtraction.critical_skills / skill_names 作为 property 派生，供 #037 落库复用。

Rationale: 内联结构让 evidence 与 critical 归属同一技能项，无两列表对齐问题；派生属性同时满足 issue 的字段口径。

Deviations

None — implementation followed the spec as written.（抽取器位置、重试语义、seniority 四档、evidence 口径均按 RIP-003 v1.1 增量设计执行）

Tradeoffs

Tradeoff extract 返回类型：dict vs JDExtraction 模型

Alternatives: ① 学 llm_extractor 返回 dict[str, Any]（校验后仍传 dict）；② 直接返回 JDExtraction。

Chosen: ②。JD 抽取结构小且封闭，强类型让 #037 落库时直接用 skill_names/critical_skills 属性，mypy 可查；llm_extractor 返 dict 是因为简历结构庞大且部分透传。也因此没继承 ResumeExtractor 基类（返回类型不兼容，语义也不是简历抽取）。

Tradeoff extra="forbid" 收紧 vs 默认 ignore

Alternatives: ① ConfigDict(extra="forbid") 拒绝多余键；② 仅必填化核心字段。

Chosen: ②。forbid 会把「多给了无害字段」的输出也打成失败，白白消耗重试次数；必填化已足够拦住空结果这一真实风险。
