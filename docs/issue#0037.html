Implementation Notes

Issue #0037 — POST /jd 自动抽取集成 + Alembic 迁移 — 2026-07-30

Design Decisions

Decision model_fields_set 区分「省略」与「显式空列表」

Ambiguity: 需求说「未显式传入 required_skills 时自动抽取」，但 JobDescriptionInput.required_skills 默认 []，真值判断无法区分 {"raw_text": "..."} 与 {"raw_text": "...", "required_skills": []}。

Choice: skills_explicit = "required_skills" in payload.model_fields_set；显式空列表走 manual 空技能分支，不触发 LLM。

Rationale: review 第 1 轮 finding：main 上传空列表的存量调用方原本「空技能、立即落库」，若误触发抽取会引入延迟、成本和 502 风险，属于隐性契约破坏。单测 test_explicit_empty_skills_skip_extraction 固化。

Decision 先抽取后 session.add，保证失败不落库

Ambiguity: 验收要求「抽取失败返回 502 且不落库」，实现顺序可以是先建 ORM 行再抽取回填，或先抽取再建行。

Choice: _get_extractor().extract() 在任何 session.add 之前执行，JDExtractionError → HTTPException(502) 时会话干净，无需回滚。

Rationale: 依赖异常触发 rollback 的写法对 _FakeSession 类测试不友好，也易在中间件层残留半提交状态；顺序前置最简单且可用 session.added == [] 直接断言。

Decision 502 用 HTTPException 而非 APIResponse(code=502)

Ambiguity: jd.py 既有端点 404 走 APIResponse(code=404, ...) 信封模式（HTTP 仍 200）；照片 API 则用真实 HTTP 状态码。

Choice: raise HTTPException(status_code=502, detail="JD_EXTRACTION_FAILED")。

Rationale: 502 语义是「上游依赖故障」，网关/监控/前端重试策略都依赖真实状态码；信封 200 会让基础设施层无法感知 LLM 故障。与验收条件「返回 502」的字面口径一致。

Decision 网关层异常在 extractor 内包装为 JDExtractionError

Ambiguity: #036 的 extract 只把 JSON/schema 校验失败包装为 JDExtractionError，gateway.complete 的网络/鉴权/超时异常会穿透为裸 500。

Choice: extract 循环内对 gateway.complete 加 except Exception 统一包装（CancelledError 继承 BaseException 不受影响），端点侧只需 catch 一种异常。

Rationale: review 第 1 轮 NIT：语义上「LLM 不可用」确属抽取失败，前端应按同一 502 契约处理；在 extractor 收口比在每个调用方重复 catch 更稳。网关错误不消耗输出格式重试次数——网络重试是 gateway 自身的职责。

Tradeoffs

Tradeoff _get_extractor 模块级 helper vs FastAPI Depends 注入

Alternatives: ① Depends(get_jd_extractor) 依赖注入；② 模块级 _get_extractor() 工厂函数。

Chosen: ②。项目单测惯例是直调端点函数 + monkeypatch（test_photo_api.py 模式），Depends 参数会迫使每个测试手动传 extractor 实例；模块级工厂 monkeypatch 一行搞定，且每请求新建实例避免 token_usage 等可变状态跨请求串扰。

Tradeoff match_resume_to_jd 现场创建 JD 未接入自动抽取

Alternatives: ① POST /jd/match 的 inline jd 分支也走抽取；② 仅 POST /jd 接入。

Chosen: ②。issue 验收范围只覆盖 POST /jd；match 场景调用方通常已带技能清单，inline 空技能 JD 依赖 ORM Python-side default（extraction_source="manual"）自动补齐新列，行为不变。若后续需要可复用 _get_extractor 低成本扩展。

Open Questions

Question 自动抽取的同步等待是否需要改异步任务？

当前 POST /jd 同步等待 LLM 抽取（含 1 次格式重试最多 2 次调用），长 JD 下响应可能达数十秒，受 uvicorn/网关超时约束。若产品要求快速返回，可改为 Celery 任务 + 状态轮询（项目已有 tasks 基建），但会改变 API 契约——待前端接入后按真实耗时评估。

Question extraction_source 是否需要第三个取值 "mixed"？

当前二值 manual | llm。若后续支持「LLM 抽取后人工修订技能清单」（PATCH /jd），修订后的来源语义既非纯 manual 也非纯 llm，届时可能需要 "mixed" 或 reviewed_at 字段——迁移已用 String(20) 预留空间。
